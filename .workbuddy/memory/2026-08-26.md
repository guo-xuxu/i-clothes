## 知识抽取结果分析 + prompt 优化

- 用户自己实现了切块（langchain RecursiveCharacterTextSplitter 的 TextChunker）+ 联合抽取（Agno+DeepSeek 的 GraphExtractor）+ 编排（DocumentProcessor），跑了 test_document_extract.py 得到 document_extract_result.txt。
- 分析抽取结果：4 chunk、51 实体、62 关系。实体质量高（命名规范、类型清晰、同义合并到位）；关系有缺陷。
- 核心问题（用户指出）：泛化大类代替「带限定条件的子实体」——「色彩 --(导致)--> 单调感」应为「色彩相近 --(导致)--> 单调感」。根因：prompt 规则 4 已写了这条但 few-shot 无对应样例 + 规则编号重复（实体 1-4、关系又从 4 开始）。
- 其他问题：关系词 13 种语义重叠（增强≈促进）、"导致"负面因果词、搭配关系 30+ 条信息量低、强度 7-9 扎堆。
- 用户定稿的优化方案：
  1. ✅ 修复编号重复（实体 1-4、关系 5-8、关键词 9）
  2. ✅ 补实体粒度 few-shot 样例（示例加「色彩相近」「单调感」实体 + 「色彩相近→单调感」关系）
  3. ❌ 不做关系词白名单——「先平铺关系，最后再映射」；且映射暂缓（只有一篇文章）
  4. ✅ 搭配单品多多益善不压制，改用「强度拉开区分度」（核心关系 9-10、泛化关系 5-6）
- 已改 `app/knowledge/build/extract/graph_extractor.py` 的 `_EXTRACT_PROMPT`（编号+规则8强度+示例增色彩相近、调整示例 strength：适合9/体现7/搭配6/导致8）。

## RAG 实现方案讨论定稿 + 文档产出

- 与用户多轮讨论，定稿以下关键决策：
  1. **指代消解**：藏在抽取 prompt（还原代词），不做独立模块。
  2. **实体消歧**：用 dimension 维度标签轻做，同一维度内才对齐，不上重型上下文向量消歧。
  3. **实体对齐**：目标「一个节点 + 记录来源」——同概念图里唯一节点，node 存 aliases+sources；L1 字符串归一 + L2 同义词典 + L3 LLM 聚类（全量后按维度分桶）。
  4. **知识融合/冲突**：软知识保留多来源（边记 sources），不硬性裁决。
  5. **存储**：图谱 networkx + graph.json 落盘 + 内存加载（不上数据库/Neo4j；networkx 无 DB 适配器，只有文件格式）；向量走 PG。规模评估：100 篇 ≈ 200-300 chunk、去重后 1000-2000 实体，networkx 绰绰有余，瓶颈在 LLM 抽取调用次数（200-300 次）。
  6. **增量构建（幂等）**：`data/processed_docs.json` 记录已抽取文档，用「路径 + 内容哈希」判断（内容改了自动重抽）；方案 B：Document 加 content 字段供切块与哈希复用。
